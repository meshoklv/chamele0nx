# Установка сервера Chamele0nX

Здесь весь путь: от пустой машины с Ubuntu до работающего туннеля.
Идите по порядку. Все команды ниже рассчитаны на свежий сервер, если не
сказано иначе.

Везде `vpn.example.com` — это ваш домен. Подставьте свой.

---

## 1. Что понадобится

| | |
|---|---|
| **VPS** | 1 vCPU и 1 ГБ RAM хватит на несколько человек. Дальше предполагается Ubuntu 22.04 или 24.04. |
| **Доменное имя** | Запись `A` смотрит на IP сервера. Не поддомен общего домена хостера. |
| **Открытые порты 80 и 443** | 80 — для проверки ACME, 443 — для всего остального. |
| **Go 1.26** | Для сборки. На сервере он не обязателен, см. кросс-компиляцию ниже. |
| **Root или sudo** | Для юнита службы, файрвола и файла sysctl. |

**Почему домен обязателен.** Вся защита Chamele0nX держится на том, что
сервер неотличим от обычного HTTPS-сайта. У обычного HTTPS-сайта есть имя
хоста, сертификат, выписанный на это имя, и браузер открывает его без
предупреждений. Сервер, который отвечает на голом IP-адресе самоподписанным
сертификатом, — сам по себе сильный признак: почти ничто законное так не
выглядит, а системы цензуры охотно реагируют на такие дешёвые признаки.
Никакой настройкой это не компенсируется.

Берите домен, имя которого подходит к сайту, который вы на него положите.
Если сайт-прикрытие — консоль поддержки, не размещайте её на
`fast-vpn-server-3.example`.

## 2. Сборка

```bash
git clone https://github.com/meshoklv/chamele0nx
cd chamele0nx
make build
```

`make build` кладёт четыре бинаря в `./bin`:

| Бинарь | Что это |
|---|---|
| `chamele0nx-server` | Сервер. Отдаёт сайт-прикрытие и туннели для прошедших проверку клиентов. |
| `chamele0nx-client` | Клиент для командной строки. Поднимает локальный SOCKS5-прокси. |
| `chamele0nx-profiler` | Снимает профиль трафика с настоящего сайта. |
| `chamele0nx-validator` | Статистические тесты: похож ли сформованный вывод на профиль. |

Данные о версии вшиваются при сборке. Посмотреть их:

```bash
./bin/chamele0nx-server -version
```

Остальные цели: `make test`, `make test-race`, `make vet`, `make lint`,
`make check` (то, что гоняет CI), `make clean`, `make help`.

### Кросс-компиляция под сервер

Если собираете на ноутбуке, а разворачиваете на Linux-VPS, соберите
статический бинарь и скопируйте его:

```bash
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 \
  go build -trimpath -ldflags "-s -w" \
  -o bin/chamele0nx-server-linux-amd64 ./cmd/chamele0nx-server

scp bin/chamele0nx-server-linux-amd64 root@vpn.example.com:/usr/local/bin/chamele0nx-server
ssh root@vpn.example.com 'chmod 755 /usr/local/bin/chamele0nx-server'
```

Для ARM-серверов возьмите `GOARCH=arm64`. `CGO_ENABLED=0` важен: он даёт
бинарь без зависимости от libc, и тот запускается на сервере, где
дистрибутив старше, чем на машине сборки.

## 3. Получите сертификат

Поставьте certbot и выпустите сертификат. Сервер слушает `:443`, а не
`:80`, поэтому порт 80 остаётся свободным для проверки HTTP-01.

```bash
sudo apt update
sudo apt install -y certbot
sudo certbot certonly --standalone -d vpn.example.com
```

Сертификат окажется в `/etc/letsencrypt/live/vpn.example.com/`.
`certbot.timer` обновляет его сам, примерно дважды в сутки, и ничего не
делает, пока до конца срока больше 30 дней.

### Повторное использование ключа при обновлении

По умолчанию certbot генерирует **новую пару ключей** при каждом
обновлении. Если хоть один клиент делает привязку к открытому ключу
сертификата, каждое обновление разом ломает всех таких клиентов, причём
рукопожатие падает ровно так, как выглядела бы атака.

Если вы делаете привязку, заставьте certbot переиспользовать ключ:

```bash
sudo certbot renew --reuse-key --cert-name vpn.example.com
```

или пропишите это насовсем в `/etc/letsencrypt/renewal/vpn.example.com.conf`:

```ini
reuse_key = True
```

Клиент командной строки из этого репозитория привязку не делает. Сторонние
мобильные клиенты на базе `mobile/` могут делать. Решите это до раздачи
клиентов: передумать позже — значит выпускать новую сборку клиента.

### Перезапуск сервера после обновления

Сервер читает сертификат один раз при старте. Заведите служебного
пользователя и каталог, который тот может читать, а затем добавьте хук
развёртывания, чтобы обновление действительно вступало в силу:

```bash
sudo useradd -r -s /usr/sbin/nologin chamele0nx
sudo mkdir -p /etc/chamele0nx/tls
sudo chown root:chamele0nx /etc/chamele0nx/tls
sudo chmod 0750 /etc/chamele0nx/tls

sudo tee /etc/letsencrypt/renewal-hooks/deploy/chamele0nx-reload.sh >/dev/null <<'EOF'
#!/bin/sh
set -e
install -o chamele0nx -g chamele0nx -m 0640 \
  "$RENEWED_LINEAGE/fullchain.pem" /etc/chamele0nx/tls/fullchain.pem
install -o chamele0nx -g chamele0nx -m 0600 \
  "$RENEWED_LINEAGE/privkey.pem"   /etc/chamele0nx/tls/privkey.pem
systemctl restart chamele0nx-server
EOF
sudo chmod 755 /etc/letsencrypt/renewal-hooks/deploy/chamele0nx-reload.sh
```

Копирование нужно потому, что `/etc/letsencrypt/live` и `archive` читает
только root, а сервер работает не под root. Положить текущий сертификат в
каталог, доступный служебному пользователю, проще и безопаснее, чем
ослаблять права на дереве certbot.

Положите текущий сертификат туда прямо сейчас, чтобы первому запуску было
что читать; дальше хук будет держать его свежим.

```bash
sudo install -o chamele0nx -g chamele0nx -m 0640 \
  /etc/letsencrypt/live/vpn.example.com/fullchain.pem /etc/chamele0nx/tls/fullchain.pem
sudo install -o chamele0nx -g chamele0nx -m 0600 \
  /etc/letsencrypt/live/vpn.example.com/privkey.pem   /etc/chamele0nx/tls/privkey.pem
```

## 4. Поставьте за ним настоящий сайт

Что лежит в `-cover-dir`, то и увидит посетитель без доступа. То же самое
увидит и тот, кто проверяет, не прокси ли этот хост.

```bash
sudo mkdir -p /var/www/cover
sudo cp -r deploy/cover-site/* /var/www/cover/
sudo chown -R chamele0nx:chamele0nx /var/www/cover
```

**А потом замените его.** `deploy/cover-site/` — нарочно невзрачная
заглушка, чтобы сервер из коробки делал что-то разумное. Если каждое
развёртывание проекта отдаёт одну и ту же заглушку, она сама становится
отпечатком, и поиск по ней находит сразу все серверы. Это ровно тот провал,
ради которого протокол и существует.

Сайт-прикрытие, который держит удар:

- выглядит как продукт, который человек мог бы разместить именно на **этом**
  домене;
- имеет форму входа, которая ошибается так же, как настоящая форма входа, а
  не возвращает один и тот же ответ на любой ввод;
- отдаёт несколько статических файлов, чтобы одна загрузка страницы давала
  всплеск запросов, а не единственный запрос;
- отвечает обычной 404 на неизвестные пути;
- не содержит ни слова про VPN, прокси, цензуру и этот проект.

Самый надёжный и самый дешёвый вариант — направить `-cover-dir` на копию
настоящего статического сайта, который вы и правда держите.

## 5. Создайте секрет

Секрет — единственный пропуск. Кто им владеет, тот пользуется туннелем; кто
не владеет, тот не может даже понять, что туннель существует.

Сгенерируйте 32 случайных байта в шестнадцатеричном виде:

```bash
openssl rand -hex 32
```

Сервер принимает любой hex-секрет от 16 байт и отказывается от более
короткого. Запущенный вообще без секрета, он генерирует его сам, печатает в
stderr и работает с ним — годится для первой проверки и бесполезно дальше,
потому что при перезапуске секрет будет другой.

### Никогда не передавайте его аргументом командной строки

`-secret <hex>` работает, и пользоваться им не надо. Аргументы командной
строки видны любому пользователю машины через `ps`, они попадают в историю
оболочки и в учёт процессов. Сервер берёт секрет из четырёх источников, в
таком порядке:

| Приоритет | Источник | Примечания |
|---|---|---|
| 1 | `-secret-file PATH` | Читает файл и обрезает пробелы. Предпочтительно. |
| 2 | `-secret HEX` | Видно в `ps`. Избегайте. |
| 3 | `$CHAMELE0NX_SECRET_FILE` | Путь. Это использует юнит systemd. |
| 4 | `$CHAMELE0NX_SECRET` | Значение. Лучше флага, хуже файла. |

Аргументы командной строки побеждают окружение, поэтому переменная,
унаследованная от оболочки или супервизора, не может тихо перебить флаг,
который набрал оператор. Клиент берёт свой секрет из тех же четырёх
источников и в том же порядке.

### Хранение через systemd credentials

Поставляемый юнит использует `LoadCredentialEncrypted`. systemd шифрует
секрет на ключе этого хоста, при старте расшифровывает его в каталог tmpfs,
который читает только служба, и передаёт путь в `%d`. Копия
зашифрованного файла, унесённая на другую машину, бесполезна.

```bash
sudo mkdir -p /etc/chamele0nx
openssl rand -hex 32 | sudo systemd-creds encrypt \
  --name=chamele0nx-secret - /etc/chamele0nx/secret.cred
sudo chmod 600 /etc/chamele0nx/secret.cred
```

Держите копию открытого hex где-нибудь офлайн. Из `secret.cred` на другой
машине его не восстановить, а потеря означает перенастройку каждого клиента.

Если в системе нет `systemd-creds`, используйте обычный файл:

```bash
openssl rand -hex 32 | sudo tee /etc/chamele0nx/secret >/dev/null
sudo chown chamele0nx:chamele0nx /etc/chamele0nx/secret
sudo chmod 600 /etc/chamele0nx/secret
```

и поменяйте последний аргумент в юните на `-secret-file /etc/chamele0nx/secret`.

## 6. Запустите как службу

Поставьте поставляемый юнит:

```bash
sudo mkdir -p /var/log/chamele0nx
sudo chown chamele0nx:chamele0nx /var/log/chamele0nx
sudo cp deploy/systemd/chamele0nx-server.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now chamele0nx-server
```

Поправьте пути в `ExecStart`, если у вас они другие. Из коробки юнит ждёт
`/usr/local/bin/chamele0nx-server`, сертификаты в `/etc/chamele0nx/tls/`,
сайт-прикрытие в `/var/www/cover` и профиль в
`/etc/chamele0nx/profile.json`. Уберите строку `-profile`, если файла
профиля пока нет; сервер возьмёт встроенный профиль для трафика от сервера.

Посмотрите, как он стартует:

```bash
systemctl status chamele0nx-server
journalctl -u chamele0nx-server -n 50 --no-pager
journalctl -u chamele0nx-server -f          # в реальном времени
```

### Что делают директивы песочницы

Юнит нарочно зажат. Коротко:

| Директива | Что даёт |
|---|---|
| `User=chamele0nx` | Не root. Взлом процесса — не взлом машины. |
| `AmbientCapabilities=CAP_NET_BIND_SERVICE` | Позволяет процессу без root занять `:443`. `setcap` на бинарь не нужен. |
| `CapabilityBoundingSet=` | Это единственная привилегия, которую он вообще может получить. |
| `LoadCredentialEncrypted=` | Секрет расшифровывается в tmpfs при старте, привязан к хосту, на диск в открытом виде не попадает. |
| `NoNewPrivileges=yes` | Изнутри процесса нельзя поднять права через setuid. |
| `ProtectSystem=strict` | Вся файловая система только для чтения, кроме `ReadWritePaths`. |
| `ProtectHome=yes` | `/home`, `/root` и `/run/user` не видны. |
| `PrivateTmp` / `PrivateDevices` | Свой `/tmp`; нет доступа к сырым устройствам. |
| `ProtectKernelTunables/Modules/Logs` | Нельзя менять sysctl, грузить модули и читать `dmesg`. |
| `ProtectProc=invisible` | Не видит процессы других пользователей в `/proc`. |
| `RestrictAddressFamilies=` | Только IPv4, IPv6 и сокеты Unix. Никаких сырых и пакетных сокетов. |
| `MemoryDenyWriteExecute=yes` | Нет памяти, одновременно доступной на запись и исполнение. Закрывает большой класс внедряемых нагрузок. |
| `SystemCallFilter=@system-service` плюс запрещающий список после `~` | Нет привилегированных, отладочных, монтирующих и пространственных системных вызовов. |
| `LockPersonality` / `RestrictRealtime` / `RestrictSUIDSGID` / `RestrictNamespaces` | Закрывает обычные побеги из песочницы. |
| `LimitCORE=0` | Никаких дампов памяти. В дампе были бы сессионные ключи и секрет. |
| `UMask=0077` | Всё, что он пишет, доступно только его пользователю. |
| `Restart=always`, `RestartSec=2` | Падение означает перезапуск, а не простой. |
| `TimeoutStopSec=40` | Остановка ограничена по времени, с запасом на то, чтобы сервер успел дожать туннели за свои 30 с по SIGTERM. |

Хотите второе мнение — оцените результат:

```bash
systemd-analyze security chamele0nx-server
```

### Все флаги сервера

Ниже всё, что принимает бинарь. Значения по умолчанию в скобках.

| Флаг | По умолчанию | Что делает |
|---|---|---|
| `-addr` | `:443` | Адрес прослушивания. |
| `-cert` | — | Цепочка TLS-сертификата, PEM. Обязателен. |
| `-key` | — | Закрытый ключ TLS, PEM. Обязателен. |
| `-api-path` | `/api/v1/events` | Путь, по которому идёт туннель. Должен совпадать с клиентом. |
| `-server-id` | `chamele0nx-1` | Идентификатор сервера. Подмешивается в токен доступа, поэтому должен совпадать с клиентом. |
| `-secret` | — | Hex-секрет. Виден в `ps`; лучше `-secret-file`. |
| `-secret-file` | — | Прочитать hex-секрет из этого файла. |
| `-cookie-format` | `generic` | `generic`, `wordpress` или `django`. Должен совпадать с клиентом. |
| `-cover-dir` | — | Каталог, который отдаётся посетителям без доступа. |
| `-profile` | — | JSON с профилем трафика. Без него берётся встроенный профиль. |
| `-idle-timeout` | `5m` | Закрывать проброшенные потоки без активности дольше этого срока. |
| `-log-format` | `json` | `text` или `json`. |
| `-log-level` | `info` | `debug`, `info`, `warn`, `error`. |
| `-disable-downstream-shaping` | `false` | Аварийный выключатель. Отключает формовку записей на стороне сервера. Ослабляет защиту; только как запасной выход для оператора. Задаётся также через `CHAMELE0NX_DISABLE_DOWNSTREAM_SHAPING=1`. |
| `-version` | — | Напечатать версию, коммит и дату сборки и выйти. |

---

### Смените умолчания, которые вас выдают

Четыре из этих умолчаний одинаковы на каждой машине, где софт запущен как
есть: туннель идёт по `/api/v1/events`, сервер откликается на
`chamele0nx-1`, кука имеет форму `generic`, а каталог прикрытия — копия
`deploy/cover-site`. Ни одно из них не секрет и ни одно не ослабляет
криптографию. Они хуже: это общий отпечаток. Сканер, разобравший одну
установку, знает форму всех остальных, и поиск каждой следующей стоит ему
одного запроса.

Поэтому выберите своё — и выбирайте под легенду, а не «наугад»:

| Флаг | Что выбрать |
|---|---|
| `-api-path` | Путь, который правдоподобно принадлежал бы сайту-прикрытию. У панели есть `/api/…`; у блога — нет, ему куда лучше идёт `/wp-json/wp/v2/…`. |
| `-server-id` | Что угодно, лишь бы не умолчание. Подмешивается в токен доступа и в открытом виде не передаётся. |
| `-cookie-format` | Движок, за который выдаёт себя сайт-прикрытие. Сайт под WordPress, ставящий куку `sid`, противоречит сам себе. |
| `-cover-dir` | Свой собственный сайт. См. раздел 4. |
| `-profile` | Профиль, снятый с того сайта, под который вы маскируетесь. См. [PROFILES.md](PROFILES.md). |

`-api-path`, `-server-id` и `-cookie-format` входят в проверку доступа,
поэтому клиенту нужно передать те же три значения. Смена этих трёх — не
ротация: уже выданные клиенты перестают подключаться, пока их не обновят,
и отказ выглядит для них так же, как для постороннего, — они получают
сайт-прикрытие.

## 7. Файрвол

По умолчанию запрет, открыты три порта, больше ничего.

```bash
sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp     # SSH
sudo ufw allow 80/tcp     # обновление ACME
sudo ufw allow 443/tcp    # сайт-прикрытие и туннель
sudo ufw enable
sudo ufw status verbose
```

Убедитесь, что больше ничего не слушает:

```bash
sudo ss -ltnp
sudo ss -ltn | grep -v '127.0.0.1'
```

Каждую строку в выводе последней команды вы должны уметь объяснить. Любой
лишний открытый порт — это второй объект для снятия отпечатка, и он может
противоречить истории, которую рассказывает сайт-прикрытие. Хосту, который
выдаёт себя за маленькую консоль SaaS, незачем светить наружу базу данных,
точку сбора метрик или второй веб-сервер на высоком порту.

## 8. Настройка TCP

Это единственное изменение с наибольшим влиянием на скорость, и к самому
протоколу оно отношения не имеет.

```bash
sudo cp deploy/sysctl/99-chamele0nx-tcp.conf /etc/sysctl.d/
echo tcp_bbr | sudo tee /etc/modules-load.d/bbr.conf
sudo modprobe tcp_bbr
sudo sysctl --system
```

Проверьте, что применилось:

```bash
sysctl net.ipv4.tcp_congestion_control     # хотим: bbr
sysctl net.core.default_qdisc              # хотим: fq
lsmod | grep bbr
```

**Что это дало, по замерам.** На длинном маршруте из сети с цензурой до
зарубежного VPS чистая скорость HTTPS с сервера выросла примерно с 3,5
Мбит/с до примерно 22 Мбит/с после перехода с CUBIC на BBR и увеличения
буферов сокетов. В протоколе не поменялось ничего. Управление перегрузкой
по умолчанию разваливается на международном маршруте с потерями, и никакая
настройка протокола потерянного не вернёт. Скорость туннеля на том же
маршруте после этого держалась около 20 Мбит/с.

Тот же файл ставит `tcp_mtu_probing=1`, из-за чего соединение не проваливается
в чёрную дыру на маршрутах со сломанным определением MTU, и
`tcp_notsent_lowat`, который держит очередь отправки в ядре короткой, чтобы
решения формовщика не тонули под многомегабайтным хвостом.

## 9. Подключите клиента

Соберите клиента на машине, с которой будете им пользоваться:

```bash
make build
```

Положите секрет в файл, а не в командную строку:

```bash
umask 077
echo '<hex-секрет>' > ~/.chamele0nx-secret
```

Запустите. Клиент поднимает SOCKS5 на localhost и держит его занятым всю
свою жизнь, заново поднимая туннель под ним при сбое с растущей выдержкой
между попытками от 1 с до 60 с.

```bash
./bin/chamele0nx-client \
  -server vpn.example.com:443 \
  -secret-file ~/.chamele0nx-secret \
  -server-id chamele0nx-1 \
  -cookie-format wordpress \
  -port 1080
```

`-server-id`, `-cookie-format` и `-api-path` обязаны совпадать с сервером.
Токен доступа — это HMAC по интервалу времени и идентификатору сервера,
поэтому при несовпадении идентификатора проверка не проходит и вы получаете
сайт-прикрытие вместо туннеля.

Проверьте туннель целиком, ничего больше не настраивая:

```bash
./bin/chamele0nx-client \
  -server vpn.example.com:443 \
  -secret-file ~/.chamele0nx-secret \
  -cookie-format wordpress \
  -check
```

`-check` поднимает туннель, забирает через него ваш внешний IP, печатает
его и выходит. Напечатать он должен адрес сервера, а не ваш. Сдаётся он по
истечении `-check-timeout` (30 с по умолчанию).

Дальше пользуйтесь прокси:

```bash
curl -x socks5h://127.0.0.1:1080 https://example.org/
curl --socks5-hostname 127.0.0.1:1080 https://ifconfig.me
```

Пишите `socks5h://` (или `--socks5-hostname`), а не `socks5://`. Буква `h`
отправляет разрешение имён через туннель. Без неё ваш DNS-сервер видит
каждое имя, которое вы открываете, а обычно именно от этого вы и уходили.

### Флаги клиента, нужные на этом шаге

Полная таблица флагов клиента — в [CLIENTS.md](CLIENTS.md). Для
подключения хватает этих, а три, которые обязаны совпадать с сервером,
названы выше.

| Флаг | По умолчанию | Что делает |
|---|---|---|
| `-server` | — | `host:port` сервера. Обязателен. |
| `-secret-file` | — | Прочитать hex-секрет из этого файла. Используйте его вместо `-secret`. |
| `-port` | `0` | Локальный порт SOCKS5. 0 — выбрать случайный свободный. |

## 10. Проверьте, что он похож на сайт

Делайте эти проверки из сети, отличной от серверной, и без запущенного
клиента. Именно это видит зондирующий.

**Браузер** при открытии `https://vpn.example.com/` должен показать ваш
сайт-прикрытие с целым замочком и без предупреждений о сертификате. Не
пустую страницу, не страницу nginx по умолчанию, не ошибку.

**GET без доступа** возвращает сайт-прикрытие:

```bash
curl -sS -o /dev/null -w 'HTTP=%{http_code}\n' https://vpn.example.com/
# ждём: HTTP=200
```

**Запрос без доступа на путь туннеля** отвечает так же, как настоящая точка,
закрытая кукой: отказывает — и отказывает одинаково на обоих методах, которые
он поддерживает.

```bash
curl -sS -o /dev/null -w 'HTTP=%{http_code}\n' -X POST \
  -H 'Content-Type: application/json' -d '{"x":1}' \
  https://vpn.example.com/api/v1/events
# ждём: HTTP=401

curl -sS -o /dev/null -w 'HTTP=%{http_code}\n' \
  https://vpn.example.com/api/v1/events
# ждём: HTTP=401 — тот же ответ, что и на POST выше

curl -sS -i -X DELETE https://vpn.example.com/api/v1/events | head -n 5
# ждём: HTTP/2 405 и заголовок «allow: GET, POST»
```

Отказ следует тому фреймворку, который назван в `-cookie-format`: кука уже
привязала сайт-прикрытие к конкретной легенде. `generic` и `wordpress`
отвечают 401, а `django` — **403**: у сессионной аутентификации Django REST
Framework нет схемы, которую можно назвать, и она понижает статус. Там ждите
403, а не 401. Заголовок `WWW-Authenticate` не шлёт ни один из них, потому что
его не шлёт то ПО, которому мы подражаем.

Тела ошибок побайтово одинаковы от вызова к вызову, и это правильно: у
настоящего API тела ошибок тоже постоянны. Меняется только заголовок
`X-Request-Id` — так его и выдаёт обычная трассировка запросов. Выдало бы
приманку другое: данные анонимному вызывающему или разные ответы на GET и
POST, будто это два разных приложения.

**Неизвестный путь** возвращает обычную 404:

```bash
curl -sS -i https://vpn.example.com/nope
# ждём: HTTP/2 404
```

Смотрите на тело, а не только на код. Если в каталоге прикрытия лежит
`404.html`, именно эта страница уходит на неизвестные пути — с кодом 404 и
с типом содержимого страницы, а не листинга. В `deploy/cover-site` она
есть, так что скопированный оттуда сайт уже согласован.

Не положить её — и ответит файловый сервер Go, а его тело 404 — простая
строка `404 page not found`: так не ответил бы сайт на WordPress или
Django, и узнаётся это мгновенно. Сайт-прикрытие, у которого страницы —
HTML, а 404 — голый текст от Go, отвечает как два разных приложения, а
такие швы активная проба и ищет. Значит: кладите `404.html`, который
выглядит частью того же сайта, что и `index.html`, и не берите движок, у
которого страница 404 настолько известна, что её отсутствие бросается в
глаза.

**Сертификат** выписан на ваш домен публичным удостоверяющим центром и
действителен:

```bash
echo | openssl s_client -connect vpn.example.com:443 \
  -servername vpn.example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

Если клиенты делают привязку к открытому ключу, запишите его отпечаток
сейчас и сверяйте после каждого обновления:

```bash
openssl x509 -in /etc/chamele0nx/tls/fullchain.pem -pubkey -noout \
  | openssl pkey -pubin -outform der | sha256sum
```

**Лишних портов** снаружи нет:

```bash
nmap -Pn -p- vpn.example.com     # с другой машины
```

22, 80 и 443. Больше ничего.

## 11. Разбор неполадок

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| Сервер выходит на старте, печатает «usage» | Не задан `-cert` или `-key` | Оба обязательны. Проверьте, что пути в `ExecStart` существуют. |
| `read secret file ...: permission denied` | Служебный пользователь не может прочитать секрет | Посмотрите `ls -l` файла. Он должен читаться пользователем `chamele0nx`. С systemd credentials используйте `%d/chamele0nx-secret`, а не свой путь. |
| `secret too short` | Секрет короче 16 байт | Сгенерируйте заново через `openssl rand -hex 32`. |
| Сервер стартует, `:443` не слушается | Нет `CAP_NET_BIND_SERVICE` или порт занят чем-то другим | `systemctl status`, затем `sudo ss -ltnp \| grep :443`. |
| Ошибка сертификата на старте | Процесс не под root не может читать `/etc/letsencrypt` | Скопируйте пару в `/etc/chamele0nx/tls` хуком развёртывания из раздела 3. |
| Браузер ругается на сертификат | Сертификат на другое имя, или просрочен, или задан только `cert.pem` | Используйте `fullchain.pem`, а не `cert.pem`. Проверьте даты через `openssl x509 -noout -dates`. |
| `curl` на `/` возвращает 404 или пустое тело | `-cover-dir` пуст, указан неверно или недоступен служебному пользователю | `ls -l /var/www/cover`. Там нужен `index.html`. |
| Клиент: подключается, потом «unauthorized», вместо туннеля сайт-прикрытие | `-server-id`, `-cookie-format` или `-api-path` отличаются от серверных | Все три участвуют в проверке доступа. Сверьте их рядом. |
| Клиент: проверка доступа проходит через раз | Расхождение часов больше окна токена | Токен меняется каждые 5 минут, предыдущее окно тоже принимается, поэтому расхождение больше ~5 минут ломает вход. Запустите NTP на обоих концах. |
| Клиент: таймаут, ответа нет вообще | Порт 443 фильтруется на маршруте или адрес заблокирован | Попробуйте из другой сети. Раздел «Если адрес заблокировали» в [OPERATIONS.md](OPERATIONS.md). |
| `-check` печатает ваш собственный IP | Трафик не пошёл через туннель | Вы проверяете не тот порт прокси, или на нём висит что-то другое. |
| SOCKS5 подключается, но ничего не грузится | Имена разрешаются локально или цель заблокирована на выходе | Используйте `socks5h://`. Затем посмотрите `journalctl -u chamele0nx-server` на предмет неудачных подключений. |
| Скорость сильно ниже скорости канала | Управление перегрузкой или сам маршрут | Раздел 8. Затем замерьте чистый HTTPS с сервера и сравните; если чистая и туннельная близки, потолок задаёт маршрут, а не протокол. |
| Скорость падает почти до нуля под нагрузкой | Несколько экземпляров сервера на одном vCPU | Держите один. Два конкурирующих экземпляра на одном ядре дают убедительный на вид полный отказ. |
| Прошло обновление, и все клиенты отвалились разом | Новая пара ключей, клиенты с привязкой | `reuse_key = True`, раздел 3. Перевыпустите с `--reuse-key` и раздайте заново, если ключ уже сменился. |

Про всё, что идёт после первого успешного подключения, читайте
[OPERATIONS.md](OPERATIONS.md).
