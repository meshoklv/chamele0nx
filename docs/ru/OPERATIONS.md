# Эксплуатация сервера Chamele0nX

[INSTALL.md](INSTALL.md) доводит туннель до рабочего состояния. Этот
документ — про то, как поддерживать его в рабочем состоянии, не спалив ни
себя, ни тех, кто им пользуется.

Сначала прочитайте [THREAT-MODEL.md](THREAT-MODEL.md). Там написано, от чего
протокол не защищает. Почти всё, что дальше, существует потому, что протокол
— не самая слабая часть развёртывания.

---

## Оператор — часть поверхности атаки

Протокол прячет трафик. Вас он не прячет. Противник, который не может
классифицировать ваши пакеты, всё равно пойдёт самым коротким путём, а самый
короткий путь обычно административный, а не технический.

| Поверхность | Что идёт не так |
|---|---|
| **Доступ по SSH** | Ключ, который открывает ещё десяток машин, превращает один взломанный ноутбук во взломанный парк. Root-вход по паролю подбирают за считаные дни после появления хоста в сети. |
| **Панель хостера** | Кто ей владеет, тот загрузится в спасательный образ и прочитает диск. Это не экзотическая атака, а штатная функция поддержки. Считайте, что диск читаем провайдером. |
| **Регистратор домена** | Владеть доменом — значит решать, куда подключаются клиенты. Угон аккаунта у регистратора уводит ваших пользователей, не трогая сервер. |
| **Платёжный след** | Карта, счёт и адрес оплаты связывают сервер с человеком. Это, как правило, самое лёгкое звено в цепочке, и никакая формовка трафика на него не влияет. |
| **То, что видит сам сервер** | Сервер подключается к тем адресам, которые просят пользователи. Он их видит. Что из этого писать в журнал — ваше решение, см. «Что писать в журнал». |
| **Ваши другие личности** | Зарегистрировать домен, оплатить VPS и администрировать машину с одного аккаунта, из одной сети или из одного профиля браузера — значит связать их вместе. |

Ничто из этого не уникально для Chamele0nX. Список здесь потому, что
операторы регулярно тратят неделю на тонкости протокола и пять минут на
настройку SSH.

## Чек-лист усиления защиты сервера

Сделайте всё это. На свежем хосте уходит около пятнадцати минут.

**Только ключи, никаких паролей.**

```bash
sudo tee /etc/ssh/sshd_config.d/00-hardening.conf >/dev/null <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin prohibit-password
EOF
sudo systemctl restart ssh
```

Проверьте, что другой файл не включает пароли обратно. Облачные образы часто
идут с `/etc/ssh/sshd_config.d/50-cloud-init.conf`, где стоит
`PasswordAuthentication yes`, а побеждает последняя подходящая директива:

```bash
sudo sshd -T | grep -E 'passwordauthentication|permitrootlogin'
```

Проверьте с другой машины, прежде чем закрывать текущую сессию. Запереть
себя снаружи сервера, устойчивого к цензуре, — обычный способ его потерять.

**Если хостер прислал вам пароль root по почте, смените его.** Он лежит и в
их почтовой системе, и в вашей. Смените, даже если вы выключили вход по
паролю: спасательная консоль хостера всё равно его принимает.

**Файрвол по умолчанию запрещает.** Раздел 7 в INSTALL.md. Убедитесь, что он
переживает перезагрузку; правила, живущие только в памяти, — это не файрвол.

```bash
sudo ufw status verbose        # хотим: Status: active, default deny (incoming)
```

**Автоматические обновления безопасности.**

```bash
sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
```

Обновления безопасности ставьте. С полными обновлениями будьте осознанны:
всё, что перезапускает сетевой стек, роняет каждый активный туннель.

**Ограничьте перебор паролей по SSH.**

```bash
sudo apt install -y fail2ban
```

**Никаких дампов памяти, никакого ptrace.** Сессионные ключи и секрет живут
в памяти процесса. Дамп памяти, записанный на диск, или отладчик,
подключённый другим процессом, отдают их наружу.

```bash
sudo tee /etc/sysctl.d/99-chamele0nx-hardening.conf >/dev/null <<'EOF'
kernel.yama.ptrace_scope = 2
fs.suid_dumpable = 0
kernel.core_pattern = |/bin/false
EOF
sudo sysctl --system
```

Поставляемый юнит systemd уже ставит `LimitCORE=0` и блокирует отладочную
группу системных вызовов; эти sysctl закрывают ту же дверь для всего
остального на машине.

**Отдельный непривилегированный пользователь.** `User=chamele0nx`, без
оболочки, без домашнего каталога, который что-то значит. Никогда не
запускайте сервер под root. Занять `:443` без root позволяет
`AmbientCapabilities=CAP_NET_BIND_SERVICE`.

**Права на файлы.**

| Путь | Владелец | Режим |
|---|---|---|
| `/usr/local/bin/chamele0nx-server` | `root:root` | `0755` |
| `/etc/chamele0nx/secret.cred` | `root:root` | `0600` |
| `/etc/chamele0nx/secret` (запасной обычный файл) | `chamele0nx:chamele0nx` | `0600` |
| `/etc/chamele0nx/tls/` | `root:chamele0nx` | `0750` |
| `/etc/chamele0nx/tls/privkey.pem` | `chamele0nx:chamele0nx` | `0600` |
| `/etc/chamele0nx/tls/fullchain.pem` | `chamele0nx:chamele0nx` | `0640` |
| `/var/www/cover/` | `chamele0nx:chamele0nx` | `0755` |
| `/var/log/chamele0nx/` | `chamele0nx:chamele0nx` | `0750` |

После любой правки юнита проверяйте песочницу:

```bash
systemd-analyze security chamele0nx-server
```

**Имена.** Ничто на машине не обязано объявлять, что оно такое. Бинарь, юнит
и каталог, названные по имени проекта, сразу говорят любому, кто получил
доступ к оболочке, что именно он нашёл. Нейтральные имена ничего не стоят.

## Гигиена домена и сертификата

**Домен должен выглядеть обыкновенно.** Это первое, на что смотрит аналитик,
и самое дешёвое для оценки. Домен, зарегистрированный на прошлой неделе, со
скрытыми данными владельца, без почтовых записей, без истории и с одной
страницей за ним, — это шаблон, который отмечают сам по себе, как бы ни
выглядел трафик.

Что помогает:

- зарегистрируйте его сильно заранее и дайте отлежаться;
- заведите записи DNS, какие бывают у настоящего сайта, и ничего
  экзотического;
- разместите на нём то, что человек и правда мог бы открыть, с первого дня,
  а не заглушку, которую вы собираетесь однажды заменить;
- сделайте сайт-прикрытие подходящим по смыслу к имени;
- держите аккаунт у регистратора за собственным сильным паролем и вторым
  фактором: потерять его — значит потерять всё, что ниже по цепочке.

**Сертификаты.** Берите публичный удостоверяющий центр. Let's Encrypt
подходит и понятен всем. Обновление автоматическое; что не автоматическое,
так это подхват нового файла сервером, поэтому оставьте хук развёртывания из
раздела 3 INSTALL.md и убедитесь, что он хотя бы раз действительно
отработал:

```bash
sudo journalctl -t chamele0nx-renew --no-pager | tail
sudo certbot certificates
systemctl list-timers certbot.timer
```

**Переиспользование ключа и привязка.** Если хоть один клиент привязан к
открытому ключу сертификата, обновление обязано переиспользовать ключ, иначе
все привязанные клиенты отваливаются разом. Настраивается это до раздачи
клиентов: INSTALL.md, «Повторное использование ключа при обновлении». Здесь
задача одна — убедиться, что настройка удержалась. Сверяйте отпечаток после
каждого обновления с тем, к которому привязаны клиенты:

```bash
openssl x509 -in /etc/chamele0nx/tls/fullchain.pem -pubkey -noout \
  | openssl pkey -pubin -outform der | sha256sum
```

Не запускайте обновление принудительно, чтобы «освежить» что-нибудь.
Публичные удостоверяющие центры ограничивают число выпусков на домен в
неделю, и сжечь этот запас во время инцидента — верный способ превратить
поправимый простой в долгий.

## Что писать в журнал, а что не писать никогда

Журнал сервера по умолчанию нарочно скудный: события работы и счётчики, без
личностей. Так и оставьте.

**Пишите свободно:** запуск и остановка службы, адрес прослушивания,
эхо конфигурации, счётчики поднятых и закрытых туннелей, трассировки ошибок
и паник, потребление ресурсов.

**Не пишите никогда:**

| Никогда | Почему |
|---|---|
| IP-адреса клиентов | Самая полезная запись для любого, кто атакует ваших пользователей, и первое, что затребуют или изымут. |
| Хосты и адреса назначения | Показывает, что пользователи открывают. Равносильно истории браузера. |
| Куки и токены доступа | Живой пропуск, записанный на диск, в журнал, а возможно, и в удалённый сборщик логов. |
| Секрет в любом виде | В том числе в трассировке падения или в отладочном дампе. |
| Какой SNI или профиль прикрытия выбрал клиент | Даёт отпечаток пользователя между сессиями. |
| Полные заголовки запроса | Содержат и user agent, и куку, и остальное разом. |

**Уровень debug небезопасен в бою.** При `-log-level debug` сервер пишет
адрес назначения для неудачных подключений и заблокированных целей. Это
данные о том, что открывает пользователь. Уровень debug — для локального
воспроизведения, а не для работающей службы. В бою должно быть `info` или
`warn`, если хотите поменьше.

**Ограничьте журнал**, чтобы логи не копились годами:

```bash
sudo tee /etc/systemd/journald.conf.d/chamele0nx.conf >/dev/null <<'EOF'
[Journal]
SystemMaxUse=200M
MaxRetentionSec=7day
EOF
sudo systemctl restart systemd-journald
```

Если хранить логи вообще незачем, храните меньше. Того, что вы не записали,
у вас не отберут.

## Смена секрета

**Что умеет поставляемый сервер.** Ядро протокола сверяет клиентский токен с
каждым настроенным секретом, за равное время, не выдавая, какой именно
совпал. Но клиент командной строки регистрирует ровно один секрет на
процесс. Значит, у одного работающего сервера один живой секрет, и смена
его — жёсткое переключение: как только загружен новый секрет, каждый
клиент, у которого остался старый, перестаёт проходить проверку и начинает
получать сайт-прикрытие.

Это значит, что сменить секрет на месте без перерыва нельзя. Зато можно
сменить, никого не отрезав, если развести две точки подключения внахлёст.

**Смена внахлёст, по порядку:**

1. Сгенерируйте новый секрет. `openssl rand -hex 32`.
2. Поднимите второй слушатель с новым секретом: ещё один экземпляр на
   втором порту или, что лучше, второй хост со своим именем и сертификатом.
   Дайте ему собственный `-server-id`, потому что идентификатор
   подмешивается в токен доступа.
3. Раздайте клиентам новую точку подключения. Дайте им время. Считайте, что
   часть не обновится неделями.
4. Следите за старой точкой, пока счётчик поднятых туннелей не упадёт до
   нуля и не останется там.
5. Только тогда выводите старый секрет из работы, и только тогда
   переиспользуйте порт.

**Никогда не меняйте местами шаги 3 и 5.** Убрать старый секрет до того, как
клиенты перешли, — это запереть снаружи ровно тех пользователей, которым
труднее всего до вас достучаться, чтобы узнать, что произошло.

**Меняйте секрет по причине и меняйте целиком.** Если секрет утёк, одной
смены мало: то, что утекло его, могло утечь и ключ SSH, и закрытый ключ
сертификата, и доступы к хостингу. Считайте скомпрометированным всё, что
лежало на той же машине.

Клиентский бинарь неизбежно содержит секрет, которым пользуется. Это
свойство симметричного клиента «в один клик», и оно означает, что любой
розданный клиент может быть разобран тем, кто его получил. Круг раздачи —
часть вашей модели угроз, а не деталь реализации.

## Если адрес заблокировали

**Сначала выясните, что именно заблокировано.** Первый порыв — винить
программу. Обычно адрес просто попал в список.

Диагностируйте изнутри затронутой страны, а не из своей сети. Сервер,
который прекрасно отвечает вам, может быть полностью недоступен для тех,
ради кого он существует. Нужна точка проверки на той стороне: пользователь,
готовый выполнить две команды, дешёвый VPS в регионе или любая доступная там
оболочка.

Изнутри затронутой сети:

```bash
# Имя ещё разрешается, и в тот ли адрес?
dig +short vpn.example.com

# TCP вообще устанавливается?
nc -vz -w 5 vpn.example.com 443
nc -vz -w 5 vpn.example.com 22

# Проходит ли рукопожатие TLS и с каким сертификатом?
echo | openssl s_client -connect vpn.example.com:443 -servername vpn.example.com
```

Затем разведите три случая:

| Наблюдение | Вывод |
|---|---|
| Рукопожатия TCP нет ни на один порт этого IP из этой страны, при том что другие хосты доступны | Заблокирован **адрес**. |
| TCP устанавливается, TLS падает или сбрасывается только для этого имени хоста, а для другого имени на том же IP работает | Заблокированы **домен или SNI**. |
| Всё устанавливается, но туннель не несёт трафик | Это не блокировка. Проблема настройки или службы; вернитесь к таблице разбора неполадок в INSTALL. |
| Соединения ненадолго проходят, потом на пару минут встают, и так по кругу | Ограничение скорости по поведению, а не статический список. Другая задача, другое лечение. |

**Что не помогает.** Переезд на другой порт: фильтрация по адресу к порту
безразлична. Переустановка операционной системы: адрес остался прежним.
Смена сайта-прикрытия или профиля: блокировку наложили до того, как что-либо
из этого рассматривали. Новый сертификат: то же самое. Каждый пункт стоит
вечера и не меняет ничего.

**Что помогает.** Новый адрес. Желательно у другого провайдера и в другой
автономной системе, потому что блокировки часто накладывают на диапазоны, а
не на отдельные адреса, и соседства со сгоревшей подсетью достаточно.
Домен оставьте, если заблокирован был только адрес; поменяйте запись `A`, и
клиенты пойдут следом. Если заблокирован сам домен, менять надо домен.

**Прежде чем переезжать**, проверьте новый адрес изнутри нужной страны: что
он вообще доступен и с какой скоростью. Проверять после переезда — значит
проверять на пользователях.

**Считайте адреса расходным материалом.** Планируйте замену, а не вечность:
держите развёртывание воспроизводимым, держите резервные копии свежими и не
стройте ничего, где единственный адрес жёстко вписан в место, которое вы не
сможете обновить.

## Ёмкость и скорость

**Потолок почти всегда задаёт маршрут, а не протокол.** Замерено на реальном
длинном маршруте из сети с цензурой: туннель шёл практически с той же
скоростью, что и обычный HTTPS с того же сервера, то есть накладные расходы
протокола почти нулевые. Четыре параллельных соединения в сумме дали не
больше одного. Собственный канал сервера показал сотни мегабит. Ограничивал
транзит между двумя странами.

Замеряйте в таком порядке и останавливайтесь, как только нашли ответ:

```bash
# 1. Отправная точка: канал клиента, вообще без вашего сервера.
curl -o /dev/null -w '%{speed_download}\n' https://speed.cloudflare.com/__down?bytes=25000000

# 2. Чистый HTTPS с вашего сервера, без туннеля. Это потолок маршрута.
curl -o /dev/null -w '%{speed_download}\n' https://vpn.example.com/<большой статический файл>

# 3. Через туннель.
curl -x socks5h://127.0.0.1:1080 -o /dev/null -w '%{speed_download}\n' \
  https://speed.cloudflare.com/__down?bytes=25000000
```

Если 2 и 3 близки, дело не в протоколе, и никакая настройка профиля этого не
изменит. Если 2 сильно ниже 1, дело в маршруте: сначала займитесь
управлением перегрузкой, потом подумайте о площадке с лучшей связностью.

**Управление перегрузкой даёт больше всего.** Переход с CUBIC на BBR с
увеличенными буферами поднял один такой маршрут с 3,5 до 22 Мбит/с —
замер сделан обычным HTTPS до сервера, а не через туннель. Это
кратность, а не проценты, и стоит один файл. См. раздел 8 INSTALL.

**Профиль формовки — размен скорости на маскировку.** Более агрессивный
профиль с короткими паузами прогоняет больше данных и даёт классификатору
более ровные тайминги для зацепки. Два поставляемых примера делают этот
размен явным: `saas-fast` — за скорость, `saas-stealth` — за прикрытие.
Выбирайте осознанно и после смены перепроверяйте через
`chamele0nx-validator`.

`-disable-downstream-shaping` существует как аварийный выключатель, а не как
настройка производительности. На маршруте выше он не помог, потому что
узким местом была не формовка. Включив его, вы снимаете ту самую защиту, на
которой построен проект.

**Не запускайте несколько экземпляров на одном ядре.** На хосте с одним vCPU
два конкурирующих серверных процесса дают полный обвал, который выглядит
точь-в-точь как сломанное развёртывание, и съедает часы. Один экземпляр на
хост. Когда сравниваете профили, ставьте опыт на втором, временном
слушателе и убирайте его потом, и никогда не направляйте его на порт, где
работает бой.

**Перезапуски не бесплатны.** Перезапуск дожимает активные туннели до 30
секунд, а потом закрывает их. Клиенты переподключаются сами, с выдержкой
между попытками, но пользователи это замечают. Копите изменения и
применяйте их пачкой.

## Резервные копии и восстановление

Сервер Chamele0nX хранит очень мало незаменимого. Сохраните эту малость, и
пересборка займёт пятнадцать минут.

| Что | Почему важно | Как хранить |
|---|---|---|
| **Секрет, в открытом hex** | Потеряете — придётся перенастраивать каждого клиента. | Офлайн, в зашифрованном виде, вне сервера. Не в репозитории. |
| **Юнит systemd** | В нём записаны все флаги запуска, на которых вы остановились. | Держите в приватном репозитории вместе с заметками. |
| **JSON профиля трафика** | Ваш размен скорости и маскировки. | Там же. |
| **Сайт-прикрытие** | Заново собрать убедительный дольше, чем всё остальное здесь. | Там же или архивом. |
| **`/etc/letsencrypt`** | Избавляет от перевыпуска под ограничениями и сохраняет ключ, если вы делаете привязку. | Зашифрованный архив, вне сервера. |
| **Бинарь сервера или точный тег его версии** | Позволяет пересобрать то же самое, а не что-то новее посреди инцидента. | Запишите версию; исходники в git. |

Не рассчитывайте, что `secret.cred` из резервной копии заработает
где-то ещё. Он зашифрован под тот хост, где создан; на новой машине это шум.
Храните открытый секрет и зашифруйте его заново на новом хосте.

Восстановление на свежей машине — это путь из INSTALL с двумя заменами:
восстановите `/etc/letsencrypt` вместо выпуска сертификата и восстановите
секрет вместо генерации нового. Если адрес поменялся, обновите запись `A` и
переждите TTL. Если адрес поменялся потому, что старый заблокировали,
прочитайте раздел выше, прежде чем считать, что новый продержится.

Проверьте восстановление один раз, на черновом VPS, до того, как оно
понадобится. Непроверенная резервная копия — это вера, а не копия.

## Обновление

```bash
# 1. Соберите новый бинарь, старый оставьте.
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 \
  go build -trimpath -ldflags "-s -w" -o chamele0nx-server-new ./cmd/chamele0nx-server
scp chamele0nx-server-new root@vpn.example.com:/tmp/

# 2. На сервере: сохраните копию для отката, запишите, что заменяете.
sudo cp /usr/local/bin/chamele0nx-server /root/chamele0nx-server.$(date +%F).bak
sha256sum /root/chamele0nx-server.$(date +%F).bak
/usr/local/bin/chamele0nx-server -version

# 3. Подмените и перезапустите.
sudo install -o root -g root -m 0755 /tmp/chamele0nx-server-new /usr/local/bin/chamele0nx-server
sudo systemctl restart chamele0nx-server

# 4. Убедитесь, что всё поднялось, — и снаружи, и изнутри.
systemctl status chamele0nx-server
journalctl -u chamele0nx-server -n 50 --no-pager
curl -sS -o /dev/null -w 'HTTP=%{http_code}\n' https://vpn.example.com/
```

Перезапуск — это единственный простой: по SIGTERM сервер дожимает
незавершённые туннели до 30 секунд, затем закрывает их, а клиенты
переподключаются сами. Обновления без простоя в однопроцессном развёртывании
не бывает. Если пауза недопустима, поднимите вторую точку подключения и
переведите клиентов на неё — та же схема, что и при смене секрета выше.

**Откат** — это скопировать сохранённый бинарь обратно и перезапустить.
Держите на машине хотя бы одну предыдущую версию и записывайте её
контрольную сумму, чтобы не решать, что восстанавливать, посреди простоя.

Прочитайте примечания к выпуску, прежде чем обновлять работающий сервер.
Смена профиля по умолчанию, формата куки или пути API меняет то, что обязаны
слать клиенты, а клиенты с несовпадающими настройками получают
сайт-прикрытие вместо туннеля, что со стороны пользователя читается как
полный отказ.
